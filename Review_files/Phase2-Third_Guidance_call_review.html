Decision Recap

Why fasteners — the case made last time, now acted on

Last call posed two options for making training and generation more tractable on a single M1 MacBook with no dedicated GPU. We went with Option B.

Option A — prune the corpus (not taken)

  • Drop Gate Valve / Tool Post categories, keep 143 cleaner assemblies
  • Would have reduced category diversity going into Phase 3 report review

Option B — scope to fasteners Taken

  • Bolt / Washer / Nut are the most abundant classes (~28% of all bodies) and the most geometrically consistent across every category
  • Keeps the full 193-folder / 7-category corpus intact for Phase 1 detection and Phase 2 ranking
  • Only the Phase 3 generation target is narrowed — a smaller, more tractable shape space
Phase 3 — Shape Generation

Narrowed to fasteners, and a real orientation bug fixed

What changed

  • Training samples restricted to fastener-type bodies only; 18 folders with zero fastener bodies excluded (Phase 1/2 corpus untouched)
  • Augmentation extended from 90°-only rotation to continuous-angle rotation plus scale/occupancy jitter
  • Non-fastener missing components still surface in the text-only "Expected Components Missing" panel — they just don't get a generated mesh

The bug, and the fix

  • Comparing only shortest/longest bounding-box extent can't distinguish a bolt's rod shape from a washer's disk shape when both share the same extreme ratio
  • Bolts were sometimes aligning their short axis onto the joint instead of their long axis
  • Fixed by using the middle extent too, and by orienting onto the open surface's real bore-axis (normal_hint) instead of the part bank's arbitrary canonical pose

Phase 3 — Detection Redesign

New per-hole candidate pipeline (surface_analyzer.py)

1. Candidate faces

  • Every free cylindrical face becomes a hole candidate — independent of the whole-face octree path, whose area threshold is calibrated for big faces, not small hole walls
  • Filtered by plausible diameter (2–50mm) and minimum depth (1mm) to exclude witness-mark slivers

2. Pattern requirement

  • A real fastener-hole pattern repeats (a bolt circle, a corner pattern)
  • A one-off bore of a "plausible" diameter (e.g. a central tool or shaft bore) is a single unmatched instance — excluded by requiring ≥2 same-diameter candidates on the same body

3. Coaxial merge

  • A counterbore + its narrower clearance bore are two separate topological faces for the same physical hole
  • Merged via bore-axis + position tolerance (3mm), keeping the wider face as the representative opening

Bore axis is derived from two parametric point samples on the face (not the bbox-thinness heuristic used for whole-face regions), which stays accurate for shallow, wide holes where that heuristic breaks down. Hole candidates bypass the octree/max_surfaces cap entirely — each is a genuine separate joint, not a duplicate of a neighboring region.

Modeling — Classifier Fix

Found via the new pipeline: an over-generalized nut/washer rule

The bug

Nut/Washer classification relies on relative shape ratios (flatness, elongation, hole presence) — but relative ratios alone can't tell a small hex nut from a large multi-hole plate; both can be "not elongated, flat, has holes." Testing the new hole-detection pipeline surfaced cases of oversized bodies landing on Nut/Washer.

The fix

  • New absolute-size gate: max_fastener_extent = 100mm — a body's longest extent must be below this to qualify for the Nut or Washer branches at all
  • Set generously above the largest real fastener observed in the corpus (a 62mm hex clamping nut)
  • Oversized candidates that would have matched the shape ratios are now explicitly logged (oversized-for-washer-or-nut) rather than silently reclassified

Infrastructure

Small but real: worker-kill timeout bug fixed

  • audit_component_types.py used unconditional p.join() right after p.kill() — on macOS, a gmsh/OpenCASCADE child that ignores SIGKILL can block that join for minutes
  • Fixed with the same bounded-polling pattern already used in dataset.py / part_bank.py — trust an already-received result before checking process liveness
  • Verified via a full post-migration audit re-run: 193/193 folders processed, 1 timeout, class balance confirmed stable vs. pre-migration

Same category of bug found twice now (first in part_bank.py's extraction worker, now here) — worth treating as a standing pattern to check whenever a new multiprocessing timeout path gets added to this codebase.

Discussion

Open items & questions for your input

1. R34 promotion criterion
R33 and R34 share the same 8-class taxonomy (unlike the R30→R33 jump, which changed taxonomies), so this should be a valid apples-to-apples AUC/AP comparison via the normal automatic promotion gate — confirming that's the right call before it's applied.
2. Fit-score floor for shape generation (0.3)
The per-hole pipeline now generates a ghost whenever a fastener type's shape-fit score clears 0.3 — chosen as a reasonable-looking floor, not yet tuned against a labelled precision/recall target. Worth discussing whether a held-out set of "known-empty vs. known-filled" holes should be built to calibrate this properly.
3. Carried over from last review
GNNExplainer interpretability (still not started), MRR below target for NodeRanker, and the 39.5% ambiguous-class bodies from the taxonomy audit remain open — none blocked on this cycle's fastener work, but still on the list.
