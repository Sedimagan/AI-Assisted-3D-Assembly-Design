2 · Novelty

Novelty proposal

Phase 1 novelty (established)

  • Geometry-driven, affine-invariant node features (elongation, flatness, sphericity, SDF mean/var, SA/V, hole count) — not just bounding-box statistics
  • Octree-based free-surface clustering to localize where a component is missing, not just that one is missing
  • Natural-language explanation layer (AIDA) grounded in GNN output, not a generic LLM wrapper

Phase 2 novelty (this review)

  • Heterogeneous relational encoder (RGATConv + TypedLinear) — separate parameter sets per component type and per joint/mate relation, derived from existing feature schema with zero data-pipeline migration
  • Node Ranker — reframes "what's missing" as "what type of component is most likely next," via a frozen-encoder + BPR-ranked prototype head — cheap to train, decoupled from Phase 1 retraining cost
  • Proposed extension (Prof. Gaurav Siwal): move from predicting a missing component's type/location to actually synthesizing its 3D geometry — discussed later as Phase 3 scope
3 · Title & Abstract

Title & abstract

AI-Assisted 3D Assembly Design: Graph Neural Networks for Missing-Component Detection and Next-Component Ranking in CAD Assemblies

This project models CAD assemblies as graphs — components as nodes, mates/joints as edges — and applies Graph Attention Networks to reason about assembly structure. Phase 1 addressed missing-component detection via link prediction over STEP-derived geometry features, supported by a template-based frequency prior and an Octree-based open-surface localizer, and delivered through a Gemini-backed explanation agent and a Streamlit/FastAPI application. Phase 2 extends the encoder to a heterogeneous, relation-aware architecture (RGATConv + TypedLinear) that gives each component type and joint type its own parameters, and introduces a Node Ranker head that answers a forward-looking question — given a partial assembly, which component type is most likely to complete it next — evaluated via Hit@K, MRR, and NDCG@K. The work is evaluated on real-world STEP assemblies spanning multiple mechanical-engineering categories, with an explicit, honestly-reported target of AUC ≥ 0.85 for link prediction that remains an open research problem addressed through architecture and data-scale experiments (R29–R31) discussed in this review.

The problem this abstract describes, in practice — a GNN-flagged missing wheel component on a bicycle assembly

Design principle carried through Phase 2

  • Node Ranker reuses the Phase 1/2 encoder frozen — only its own small projection layer is trained, so encoder retraining (R29 → R30 → R31) and ranker retraining stay independent, cheap, and clearly attributable
  • Both heads write to separate checkpoints (best_serving.pt vs node_ranker.pt) with an explicit staleness guard tying the ranker to the encoder it was trained against
5 · Algorithm / Techniques

Algorithm & techniques

Heterogeneous encoder

  • Node type = argmax of the existing 8-way component one-hot
  • Edge type = argmax of the existing 4-way joint one-hot (rigid/revolute/slider/cylindrical)
  • TypedLinear: per-type input/output projection (8 small Linear layers)
  • RGATConv × 3 layers, replacing homogeneous GATConv — every layer now relation-aware, not just layer 1

Node Ranker

  • Leave-one-node-out training task: remove a real node, encode the remainder, mean-pool → context vector
  • Candidates: 8 fixed component-type prototypes (mean raw feature vector per type, embedded frozen)
  • Loss: BPR (Bayesian Personalized Ranking) — true type ranked above the other 7
  • Metrics: Hit@K, MRR, NDCG@K

Training infra

  • 5-fold CV, early stopping (patience 20), ReduceLROnPlateau
  • Category-weighted loss (CATEGORY_WEIGHTS) to offset per-category yield imbalance
  • Checkpoint promotion gate: new run only replaces best_serving.pt if it beats the incumbent on both AUC and AP
  • train_monitor.sh: stall-detection + auto-resume watchdog for long unattended runs

5 · Algorithm / Techniques — Training History

Fold-level variance & what R31 taught us

Architecture lever confirmed real

  • R30's heterogeneous encoder beat R29 on both AUC (+5.8%) and AP (+3.1%) on the identical corpus — a genuine, isolated architecture win
  • Best single fold ever seen: 0.773 (R30, fold 4) / 0.771 (R29, fold 2) — the model can reach far higher AUC on favorable splits; the mean is dragged down by small-corpus variance, not a hard ceiling

Data-scale lever did not pay off (yet)

  • R31 nearly doubled the corpus (248 → 484 graphs) but scored essentially flat on AUC and worse on AP than R30 — more data alone, without addressing per-category quality/yield, isn't sufficient
  • Along the way, found and fixed two real infra bugs: MPS OOM at batch_size=32 on the larger/denser corpus (fixed → 16), and a training-loop stall-detector false-positive (fixed via heartbeat logging)
  • Promotion gate did its job — best_serving.pt stayed on R30, no regression shipped

Guidance Follow-up

Suggestion — move training to the cloud (M1 limitations)

Why it came up

  • During the first guidance call, the suggestion was raised: if the MacBook M1's unified-memory ceiling is limiting training, evaluate cloud GPU compute as an alternative
  • Directly motivated by what R31 exposed on this hardware: repeated MPS backend out of memory crashes (~17 GiB / 20.13 GiB ceiling), individual epochs stretching to 8,073s under memory pressure, and full 5-fold CV runs already taking 11.5–19+ hours wall-clock even when nothing fails
  • A larger, higher-quality corpus (the next lever toward AUC ≥ 0.85 per the R31 lesson) will only make single-machine M1 runs slower and more fragile, not less

What we did

  • Researched cloud GPU rental providers directly comparable to this workload: RunPod, Vast.ai, Lambda Labs
  • Priced both a cheap/spot tier and a reliable on-demand tier, since our own local runs already needed several manual recoveries from stalls/OOM — spot preemption would add a second, independent failure mode on top of that
  • Projected real cost in INR against the remaining Phase 2 workload — next slide

Reading this honestly

  • The $2–3/hr tier is the realistic one for this project — spot pricing is cheaper but interruptible, and our own local training history shows this workload already needs babysitting through stalls/OOM without adding preemption risk on top
  • 360 hours is a floor, not a ceiling — it assumes exactly 15 runs at exactly 24h each; several of our actual runs (R29 ~19h, R31 with retries much longer) already sit at or above that per-run estimate
  • Estimate excludes storage, data egress, and idle-VM billing during setup/data-upload — real spend would run higher in practice
  • ₹70,000 – ₹1,05,000 over just 5 weeks, for an individual MTech project, against $0 marginal cost on already-owned M1 hardware
Guidance Follow-up — Decision

Decision — stay within the original Phase 1 scope

"The solution is implemented entirely in Python using PyTorch Geometric, without dependency on proprietary CAD software APIs." — and the dataset curation for this project was explicitly "sized for M1 MacBook Pro training within individual project submission constraints."
— README.md, scope established with Prof. Sagarika Borah during Phase 1

Given the cost research above, staying on local M1 training

  • ₹70,000–₹1,05,000 for 5 weeks of cloud compute is disproportionate for an individual, self-funded MTech project — the original scope was deliberately sized to run on personal hardware, not a recurring cloud budget
  • The real lesson from R29→R30→R31 wasn't "we need more compute" — it was "architecture changes help, raw data volume alone doesn't" — a lever we can keep pulling locally without added spend
  • Cloud compute stays a documented, costed option — not adopted now, but available if a future phase's scope explicitly requires it
Guidance Follow-up

Suggestion from Prof. Gaurav Siwal

From prediction to synthesis

During the Phase 2 guidance call, Prof. Siwal raised a natural extension of the current scope: the system today predicts that a component is missing, where it likely belongs, and what type it probably is — but stops short of producing the component itself. The suggestion was to explore whether the project could also generate an actual 3D model of the missing component, not just describe it.

  • Would close the loop: detect → localize → classify → generate → (eventually) insert into the assembly
  • A substantial scope increase — geometry synthesis is a different ML problem class (generative 3D modeling) from the graph classification/ranking done so far
  • We scoped two candidate technical approaches (Path A / Path B, next slides) and assessed both against the remaining Phase 2 timeline

Recommendation

Recommendation for the remaining Phase 2 window

Stay focused on what Phase 2 already committed to

  • Re-run train_ranker.py against R30's heterogeneous encoder — current Node Ranker metrics are stale (trained on a superseded encoder)
  • Keep iterating on encoder retraining (R32+) toward the AUC ≥ 0.85 target — the architecture lever (R29→R30) is proven real; the next lever to try is per-category data quality/yield, not just raw volume (R31's lesson)
  • Finish the two items already committed in the Phase 1 report but not yet started: heterogeneous edge-type ablation follow-ups and GNNExplainer integration for interpretability
  • Continue training locally on M1 — cloud GPU compute was costed (≈₹70,000–₹1,05,000 for 5 weeks) and consciously not adopted, staying within the scope defined with Prof. Sagarika Borah in Phase 1

Defer 3D generative completion to Phase 3

  • Path A / Path B are real, scoped options — but both require dataset work and evaluation infrastructure that would crowd out finishing Node Ranker and the AUC push if started now
  • Proposing this explicitly rather than silently dropping it, so it's on record as a deliberate sequencing decision, not an oversight
