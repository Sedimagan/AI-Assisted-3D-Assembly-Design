Slide 2 — Title & Abstract

Business Problem card: the yellow-bordered card exists specifically to answer "why does this matter" before any technical content — invigilators often want the motivation stated explicitly, not inferred.

Abstract card names four system components in one paragraph: GAT (core prediction), AIDA (explanation), Assembly Completeness Model (template-based gap analysis — this is the AssemblyTemplateDB), Octree detector (spatial open-surface localisation). Note the phrase "no proprietary CAD API dependency" — a deliberate contrast with commercial tools (SolidWorks API, Fusion360 API) that would lock the system to a paid CAD platform. gmsh + OpenCASCADE + trimesh are all open-source.

Key Contributions list: six bullets, each corresponds to a distinct deliverable. The "22-dim node + 6-dim edge features" bullet is worth knowing cold — see Slide 11 below for the exact breakdown.

Project Details table: Phase 1 runs May 10 – Jul 10, 2026 (dates matter if asked "are you on schedule" — you are, this review lands right at the boundary). Phase 2 is Jul 10 – Sep 10, 2026.

Interpretation point: this diagram encodes a design decision — inference is decoupled from training. In normal operation, the Engineer never trains anything; training is a one-time/maintenance operation, not part of the per-upload flow. If asked "does the engineer retrain every time," the answer is explicitly no.

Slide 4 — Overall Design

image: docs/system_architecture.png

Six-stage pipeline, read left to right:

Stage 1 — Parsing: STEP file → gmsh + OpenCASCADE (parse, fragment() to split touching solids, contact detection, bbox, volume) → trimesh (exact surface area, SDF ray-casting for mean+variance) → Type Inference (SDF + bbox heuristics → 8-class component typing).

Stage 2 — Graph Construction: PyG graph assembled. 22-dim nodes (type one-hot + vol + SA + bbox + shape + SDF + SA/V + holes), 6-dim edges (mate type + weight + joint type). Feeds into AssemblyGNN — 3-Layer GAT Encoder.

Caution on this specific diagram: the box labelled "3-Layer GAT Encoder" shows hidden-dim progression 22 → 1024 (8 heads) → 512 (4 heads) → 64 (1 head). That is the R15/R16-era architecture. The current deployed architecture (R17 onward, including R22 and R28) uses a leaner 128 → 128 → 64 hidden-dim progression with the same [8,4,1] head structure (confirmed in Slide 11's "GAT Architecture Comparison" table and in the actual model.py/config.yaml). The diagram is manually maintained and hasn't been redrawn since the hidden-dim shrink at R17. If asked directly about current hidden dims, say 128→128→64, not 1024→512→64. Similarly, the "Dataset: 1,760 graphs · 24,811 nodes · 33,166 edges" side-annotation reflects the R17 snapshot, not the current R28 serving dataset (695 graphs, single category) — quote Slide 7 (Experimental Results)'s R28 card instead.

Stage 4 — Analysis: three parallel consumers of the graph/embeddings — LinkPredictor MLP (→ AUC-ROC, Avg Precision), AssemblyTemplateDB (→ assembly type + missing types), Octree Open Surface (→ open joint surfaces, citing Borah & Borah 2020).

Stage 6 — UI: Streamlit dual-panel — left is the 6-section colour-coded AI analysis panel, right is the Plotly Mesh3d 3D viewer with overlays. The legend on the diagram defines overlay colours: red = not assembled, orange = auto-ref missing, lime = open joints, blue = GNN predicted links, teal = template missing, purple = assembly type. Know these — you'll be pointing at these colours during the demo.

Right-column tables on Slide 4 itself (not the architecture image): Graph Schema table repeats the 22/6 dims; Dataset table shows the current curation numbers — 300 curated STEP files → 239 valid, 61 skipped (19 timeouts + 42 errors), avg 31.9 nodes / 81.8 edges per graph, 70/15/15 train/val/test split.

Slide 9 — R22 Training Curves & Fold Analysis

Left panel (per-epoch curves): training loss falls from ~0.54 with exponential decay; Val AUC rises toward a peak of 0.6246 at epoch 72 before a slight late decline (mild overfitting signature after the peak — good answer if asked "does your model overfit": mildly, late, and it's why early stopping / best-checkpoint saving matters); Test AP climbs more steadily toward ~0.762.

Right panel (5-fold bars): Fold 3 starred as best (Val AUC 0.6246), dashed teal line at mean Test AUC across folds.

Reconciling two "R22" numbers: the mean Test AUC across all 5 folds is ~0.588 (per the underlying fold data), while Slide 7's headline "0.626" figure is the best/promoted fold's Test AUC. If asked to reconcile: "the headline number is the best-fold value; the full fold spread is 0.54–0.67, shown on Slide 10."
Technical honesty note: this slide's canvas charts are generated by a small deterministic seeded-random function (mulberry32) that interpolates toward the real summary statistics (peak Val AUC 0.6246 at ep72, final AP ~0.762) — it's a smoothed illustrative curve anchored to real numbers, not a raw per-epoch training-log readout. If asked directly "is this the actual logged loss curve," the accurate answer: "the start/end/peak values are the real R22 fold-3 statistics; the per-epoch curve shape is a smoothed illustrative interpolation for the visual." Better to volunteer this proactively than be caught overclaiming.

Slide 11 — Model Comparison

Feature Dimension Evolution table: the standout jump is 16-dim (R8–R14 avg: AUC 0.624, AP 0.734) → 18-dim (R15: AUC 0.726, AP 0.917) — +10 points AUC, +18 points AP from one change: replacing raw, scale-dependent bounding-box numbers with affine-invariant descriptors (elongation, flatness, aspect ratios, sphericity) that stay constant regardless of a part's scale/rotation/position.

Conceptual explanation if asked "why did that help so much": a raw bbox width feature means different things for a 10mm bolt and a 500mm shaft; a ratio-based feature (elongation = long axis / short axis) means the same thing regardless of absolute part size, so the GNN learns one consistent rule instead of being confused by scale.

Node Features (22 dims, R18+) — confirmed against the actual dataset.py implementation:

DimsFeatureReal source
[0–7]8-class type one-hotrule-based cascade on bbox ratios + SDF thresholds — not ML-inferred, a geometric heuristic
[8]log1p(volume), clipped 13.8gmsh
[9]log1p(surface area), clipped 11.5trimesh
[10–12]bbox Δx/Δy/Δz (normalised)gmsh
[13–14]elongation, flatnessbbox axis ratios
[15–17]aspect x/y, y/z, sphericitybbox + trimesh (sphericity = π^(1/3)(6V)^(2/3)/SA, clipped to 1.0)
[18–19]SDF mean, SDF variancetrimesh inward ray-casting, ~300 samples/body

GAT Architecture Comparison: node dim grows 13→22 over the project; edge dim jumps 2→6 at R18 (same joint-type addition). Hidden dims shrink from 1024→512→64 (R15–16) to a leaner 128→128→64 from R17 onward — a deliberate capacity reduction given small graph counts (270–1000 graphs is small for a 1024-wide hidden layer). Heads stabilise at [8,4,1] from R15 onward. Hard-negative sampling switches on at R15 (0.3× weight); negative ratio halves from 1.0 to 0.5 at the same point.

Dataset Scaling Impact table — compact version of the "scale vs quality" story: 25 → 780 → 416 → 270 (R14: 0.624) → 270+P1-6 (R15: 0.726) → 1,760 (R17: 0.625) → 995 (R18: 0.483) → 444 (R20: 0.503) → 89 (R21: 0.428) → 239 curated (R22: 0.626, ◈ Val≈Test) → … → 695 (R28: 0.5455, current serving).

Slide 12 — Challenges & Counter Actions

Five red/amber challenge rows on the left, five teal "New Learnings" on the right, plus a Phase 2 action list. Treat this as your strongest slide for demonstrating engineering maturity — structured as problem → root cause → concrete counteraction.

#ChallengeDetail
1Dataset Parsability (61/300 failed)19 timeouts + 42 geometry errors. Real code detail: timeouts enforced at 120 seconds via a child-process wrapper (terminate() → 5s grace → kill()). Complex assemblies disproportionately time out because gmsh's fragment() is combinatorially expensive on complex boundary topology.
2AUC Target Gap (0.85 not met, best 0.726)Honestly reported as still open. Category-focus (R22) recovered generalisation (Val≈Test) but not the raw AUC bar — carried into Phase 2 as category-specific model heads + larger capacity.
3Scale vs QualityR17's 1,760 graphs scored worse than R15's 270 — headline empirical finding of the project so far.
4Category Diversity (R20: AP 0.835→0.749)A bolt-to-shaft joint and a PCB-to-enclosure joint have fundamentally different local graph topology (fastener assemblies dense/rigid-dominant; electronics assemblies sparse/positional) — a single shared GAT head has to average across contradictory patterns, hurting both.
5Training Instability (some epochs 1,024s vs typical 4–9s)Attributed to MPS device contention. Caveat: the actual fix is a device-selection priority order (MPS checked before CUDA/CPU) plus the best_serving.pt gate — no separate dedicated "MPS bug workaround" exists beyond that ordering choice.
"Serving Gate is Essential Infrastructure" — the claim of "prevented 4 regressions across 25 runs" refers to a lexicographic (mean_auc, mean_ap) tuple comparison in train.py: a new run only overwrites best_serving.pt if strictly better on that tuple than the incumbent. R20, R21, R23, R24 all computed worse tuples and were correctly held back.

Phase 2 Actions: category-specific GAT heads (→ challenge #4), 256-dim hidden capacity (→ challenge #2), automated STEP repair pipeline (→ challenge #1), 5+ categories with per-category serving gates (scaling the R22 strategy rather than reverting to R20's approach).
