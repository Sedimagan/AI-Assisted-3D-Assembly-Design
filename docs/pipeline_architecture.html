End-to-End Pipeline Architecture

A single frozen graph encoder, trained once on link prediction, feeds three independent task heads — missing-component detection (Phase 1), next-component ranking (Phase 2), and missing-shape generation (Phase 3) — plus a template-based frequency prior, an open-surface/hole geometry detector, and a Gemini-backed explanation agent, all served through a FastAPI backend and a Streamlit dual-panel UI.

Every feature below is tagged with the run that introduced it — R35 or R36 — so this page always cites exactly when and where a change landed, not just that it's "new." See Run Provenance for commit hashes, dates, and results per run, and the changelog for the full list grouped by run. This page is updated alongside the codebase — if you're reading this during an active retrain, check Run Provenance for whether the latest run has landed yet.

0 · Data Pipeline — Corpus → Attributed Graph back_end/dataset.py

Every phase shares one graph representation, built once per STEP file and cached. Nodes are solid bodies; edges are detected mate contacts. This section is the foundation everything else is built on — most of this retrain cycle's fixes live here.

0.1STEP Parsing (gmsh + OpenCASCADE)

Each STEP file is parsed independently in a spawned subprocess with a 300s wall-clock timeout (polled in short increments rather than one blocking join — a single OpenCASCADE call can be uninterruptible, and macOS has been observed to hold up SIGKILL reaping for large C++ processes).

  1. gmsh.merge(step_path) loads the file; requires ≥2 solid volumes to count as an assembly.
  2. gmsh.model.occ.fragment(volumes, []) — the key step: booleans all volumes together so that surfaces shared by ≥2 bodies get a single shared face tag. This is what turns "touching geometry" into a detectable graph edge.
  3. Per body: bounding box, mass/volume, center-of-mass, and boundary face tag set (body_surfs[i]) via gmsh.model.occ.
  4. gmsh.model.mesh.generate(2) triangulates all surfaces (best-effort — wrapped so one unmeshable periodic surface doesn't abort the whole file's other bodies).
  5. Per body, a trimesh.Trimesh is rebuilt from that body's triangulated faces for exact surface-area and SDF (Shape Diameter Function) computation via inward ray-casting — approximates CGAL's SDF without the CGAL dependency.

0.2Component-Type Classification

Multi-signal geometric voting over an 8-class taxonomy — long_shaft, short_shaft, thick_plate, thin_plate, bolt, washer, nut, body (catch-all). No single rule decides a class; each candidate class needs multiple signals to agree.

Hole detection

Convex-hull volume ratio and a central-axis ray probe must both vote for a through-hole before washer/nut branches are even considered.

Bolt-head detection

Bounding-cylinder fill ratio + center-of-mass axial offset + B-Rep face count — 2 of 3 must agree before a round, elongated body is called a bolt over a plain shaft.

Absolute-size gate

max_fastener_extent (100mm) — relative shape ratios alone can't tell a small hex nut from a large multi-hole plate; caps how large a body can be and still land on washer/nut.

Everything else falls back to elongation/flatness ratios (long vs. short shaft, thick vs. thin plate), with body as the honest catch-all when no branch fires confidently. A full-corpus audit found ~39.5% of bodies flagged ambiguous by the voting rules — reported honestly, not hidden, and open for further threshold tuning.

0.4Edge Detection & Feature Vector — 6 dimensions

Two bodies get an edge iff their boundary face sets intersect after fragment() — i.e. they share real geometry, not just a nearby bounding box. Contacts are deduplicated to one edge per body pair, then built bidirectionally.

The single most consequential bug found this cycle: all 6 edge dimensions, and node dim [21] above, were sourced exclusively from an assembly.json sidecar file that has never existed in the real 193-STEP-file corpus. Every edge's mate-type and joint-type one-hot were silently constant across every training run from the project's earliest retrains through R34. In model.py, the encoder resolves an edge's relation type via edge_attr[:,2:6].argmax() — on an all-zero slice this always returns index 0, so 3 of the 4 relation-specific attention weight matrices in RGATConv never received a training signal, in any run, ever. The "heterogeneous" relational encoder introduced in R30 was functionally a plain GAT with wasted parameters. Fixed by deriving these values from geometry directly (below) — the JSON path is kept as an optional override if a richer metadata source is ever available, but the geometry fallback is what actually runs today.

DimsFeatureHow it's derived now
[0]Mate type (normalised 0–1) R35 geometry-derived from the shared contact surface(s)' geometric type: cylindrical face(s) → concentric, planar → coincident, otherwise → other
[1]Weight R36 real contact-surface area ÷ the smaller body's total surface area, clipped [0,1]. Still hardcoded 1.0 as of R35 (only dims [0] and [2:6] were fixed that run) — every edge regardless of whether it was a flush mating face or a token touch
[2:6]Joint type one-hot (rigid / revolute / slider / cylindrical) R35 geometry-derived — cylinder-only shared face → revolute; cylinder + plane → cylindrical; plane-only → rigid; anything else → slider

0.5Spatial Position R36

Every parsed Data object now also carries pos — each body's AABB center, scaled by the assembly's own bbox_max — via PyG's standard pos attribute.

Before this, the model had zero geometric proximity signal anywhere. All 22 node features are affine-invariant shape ratios; message passing only ever runs along real edges, so when LinkPredictor scores an arbitrary candidate (non-edge) pair, it had no way to express "these two bodies are nowhere near each other." centers[i]/coms[i] were already computed during parsing but only ever fed into a body's own relative signals (e.g. bolt-head center-of-mass offset) — never exposed to the model. See LinkPredictor for how this is consumed.

0.6Dataset Caching & Train/Val/Test Splitting

Parsed graphs are cached per-file (graph_cache/) so restarts and re-runs skip already-parsed files; --force-reload rebuilds the collated dataset but this per-file cache must be cleared separately when the parsing/feature logic itself changes, or stale cached graphs get silently reused.

Test carve-out R36 hash-stable

Each graph's test/train-val membership is a deterministic hash of its own (category, source path) — adding or removing graphs elsewhere in the corpus never reshuffles an existing graph's membership. Replaces a plain torch.randperm(n), which reshuffled entirely whenever the corpus size changed — confirmed to have made a Phase 3 "regression" partly a measurement artifact (two runs at n=188 vs n=192 drew almost entirely different 28-graph test sets).

CV fold split R35 category-stratified

StratifiedKFold over the remaining train_val graphs, keyed on category. Corpus categories range from Bench_vice (54 graphs) to Tool_Post (8) — an unstratified split could leave a fold with zero Tool_Post examples, a confirmed contributor to large per-fold AUC variance. Verified every one of the 7 categories appears in every fold's validation set.

A pure hash-based fold split (matching the test carve-out's approach) was tried first and measured to regress this — it left Tool_Post with zero validation examples in 3 of 5 folds. Reverted for the fold half specifically, since fold assignments are only ever used within one training run and don't need the cross-run stability the test set does.

1 · Phase 1 — Missing-Component Detection link prediction

Given a (possibly partial) assembly graph, score every candidate node pair on how likely it is to be a real mate — i.e. "is a component missing here?" Trained once; its frozen encoder feeds Phases 2 and 3.

1.1AssemblyGNN Encoder model.py

A 3-layer relational GAT with type-aware processing at both ends:

TypedLinear (in)8 per-type input projections, dispatched by node's true type
→
RGATConv ×3128 hidden, heads [8,4,1], num_relations=4, edge_dim=6 (layer 1 only)
→
TypedLinear (out)8 per-type output projections → 64-dim embedding
  • Layer 1 injects edge features directly (edge_attr); layers 2–3 use only the relation type derived from it.
  • Relation type per edge = argmax(edge_attr[:,2:6]) — now meaningfully non-constant thanks to the geometry-derived joint features above.
  • BatchNorm + ELU + dropout (0.2) after layers 1–2.
  • 2,441,809 total trainable params (encoder + LinkPredictor combined).

1.2LinkPredictor

score(u,v) = MLP( z_u ‖ z_v ‖ distance(u,v) ) — a scalar logit per candidate edge.

R36 The MLP's first layer grew from in_dim×2 → hidden to in_dim×2+1 → hidden to accept one extra scalar: the Euclidean distance between the two bodies' pos values (already scale-normalised per assembly). pos=None degrades to a zero-filled distance for callers without positions. This changed the predictor's weight shape, breaking strict-load of any pre-R36 checkpoint — held back until the retrain that makes it meaningful, to avoid a window where the live app couldn't load its model. That retrain landed: R36 beat R34 by +0.0716 mean AUC and was promoted to best_serving.pt — this is now the live, deployed architecture, not a pending change.

1.3Training Loop train.py

  1. 5-fold cross-validation — a fresh gnn+lp per fold, Adam optimizer, ReduceLROnPlateau scheduler.
  2. Per-graph edge split via PyG's RandomLinkSplit (10% val / 10% test edges per graph, neg_sampling_ratio=0.5). R35 disjoint_train_ratio=0.25 — without this (PyG's default 0.0), train supervision edges were identical to train message-passing edges, so the encoder could see the very edges it was being scored on during training; val/test never had this leak. 25% of each graph's training edges are now held out of message passing too, closing most of that train/eval task mismatch.
  3. Loss: BCE on positive+negative edges, plus a hard-negative term — the most similar non-neighbour node to each positive edge's source is mined via embedding cosine similarity each batch and penalised at 0.3× weight.
  4. Category sample weighting — inverse-frequency weights (capped 3.0×) applied per batch so Tool_Post (8 graphs) isn't drowned out by Bench_vice (54).
  5. Checkpoint selection R35 — compares/saves against a 3-epoch trailing average of validation AUC, not the raw single-epoch value. R34 fold 3 hit val AUC=0.7364 on one lucky epoch (≈33-graph val set), saved that checkpoint, and its test AUC came back at 0.4899 — a 0.25 gap this directly targets.
  6. MPS-specific memory hygiene: periodic gc.collect() / torch.mps.empty_cache() within an epoch and at fold boundaries — variable-sized graph batches otherwise leave MPS's per-shape compiled-graph cache growing unbounded (observed RSS climbing to 19–51GB, swap thrashing).

1.4Evaluation & Promotion Gate evaluate.py

AUC-ROC and Average Precision per fold; mean ± stdev reported across the 5 folds. A new run is promoted to best_serving.pt only if it beats the incumbent on both mean AUC and mean AP — an automatic, evidence-based gate that has correctly held back multiple retrains this project (R32 vs R30, R35 vs R34) when they didn't actually improve — and correctly promoted R36 when it did (Mean AUC 0.6277±0.0516 vs R34's 0.5561±0.0257).

Reading AP honestly: with neg_ratio=0.5, a random classifier's expected AP is 1/(1+0.5) ≈ 0.667, not the usual 0.5 — so an AP of 0.74 is only ~0.07 above chance, not the "74%" it superficially looks like. AUC (chance = 0.5 regardless of class ratio) is the more honest single number to track.

2 · Phase 2 — Next-Component Ranking NodeRanker

A different question from Phase 1: not "does this edge exist," but "given this partial assembly, which of the 8 component types is most likely the next/missing one?"

2.1Design model.py

Partial graph→ frozen AssemblyGNN → mean-pool
→
proj (64×64)only this layer trains
→
cosine similarityvs. 8 type-prototype embeddings
→
score × exp(logit_scale)R36 learnable temperature
  • Candidates = the 8 fixed component types, not arbitrary real graph nodes.
  • Type prototypes = mean raw 22-dim feature vector per type (from train+val graphs), embedded through the frozen encoder as a zero-edge batch — recomputed fresh every time the encoder changes.
  • R36 code landed, retrain pending logit_scale — a CLIP-style learnable scalar multiplying the cosine similarity before the loss. Plain cosine similarity is bounded [-1,1], so raw score differences fed into BPR were small and the loss gradient sat in a flat region for a head this thin (~4.2K params in proj alone). Initialised to exp(0)=1.0 — identical to the old unscaled behaviour until training says otherwise. infer.py loads existing checkpoints with strict=False so this addition doesn't break them; the parameter just defaults to its identity value until the head is next retrained — landed in the R36 commit but Phase 2 hasn't been retrained since, so this has not yet run against real data.

2.2Training & Evaluation train_ranker.py

  1. Leave-one-node-out sampling: remove a real node from a training graph, encode the remainder through the frozen encoder, mean-pool to a context vector.
  2. BPR loss (Bayesian Personalized Ranking) pushes the true removed node's type-prototype score above the other 7 types'.
  3. Metrics: Hit@1, Hit@5, MRR, NDCG@5, each compared against a majority-class baseline.

Known open issue, not yet fixed: Hit@1 has landed at or below the majority-class baseline across every encoder generation retrained against so far (R28-era, R30, R33, R34). Diagnosed as likely architectural — proj only ever transforms the query side; the 8 prototype embeddings it's compared against are never touched by anything trainable, so Hit@1 is capped by however separated those prototypes already are coming out of the frozen encoder. Combined with zero class-imbalance handling in the leave-one-out sampling. Fix is queued (project-tracked, not yet implemented) for after Phase 1 settles on a promoted encoder.

3 · Phase 3 — Missing-Shape Generation fastener-scoped

Given a predicted-missing component type and a target open-joint region, produce an actual 3D mesh. Generation is scoped to fasteners (bolt/washer/nut) only — detection of all 8 types is unchanged; non-fastener misses still surface in the text-only expected-components panel, they just don't get a ghost mesh.

3.1Part Bank part_bank.py

A separate corpus walk (STEP files re-parsed, this time keeping the per-body meshes dataset.py discards) builds a library of real part shapes:

  1. Canonicalize — center at centroid, align to OBB principal axes, scale to unit max-extent.
  2. Voxelize — 32³ occupancy grid, 1.2× padding beyond the part's own extent.
  3. Index by (component_type, category, bbox) for nearest-neighbour retrieval at inference time.

4,500 parts from 193 assemblies after a meshing-resilience fix let STEP files with periodic (unmeshable) surfaces contribute their other bodies instead of aborting the whole file — up from 3,221. No quality gate currently exists on these newly-admitted bodies (open item, tracked separately).

3.2Conditional Shape VAE shape_generator.py

Encoder4× Conv3d blocks, 32→64→128→256 channels, stride 2
→
μ, log σ² 128-dim latent
→
Decoder4× ConvTranspose3d, 256→128→64→32→1

77-dim conditioning vector: 64-dim frozen-encoder context + 8-dim type one-hot + 3-dim target bbox + 2-dim neighbor-scale — concatenated with the latent before decoding, so the same VAE can generate any of the 8 types at any target size.

Loss: BCE + λ_dice·soft-Dice + β_KL·KL (λ_dice=0.5, β_KL=0.05) on voxel occupancy.

3.3Hybrid Orchestration

ShapeRetriever (first choice)

Nearest-neighbour lookup in the part bank by bbox-shape similarity, rescaled to the target bbox via fit_to_bbox(). Zero training, and usually wins for standardized fastener shapes.

ConditionalShapeVAE (fallback)

Used only when retrieval's fit_score falls below a threshold — retrieval_tau=0.6 generally, retrieval_tau_fastener=0.4 for bolt/washer/nut specifically (the bank already has hundreds of real examples; a slightly-imperfect real one usually beats a VAE hallucination).

rotate_to_target_axis() then orients the chosen mesh onto the real open-joint's bore axis (normal_hint, from surface_analyzer.py) instead of keeping whatever pose the part bank canonicalized it in — using the middle extent (not just shortest/longest) to correctly distinguish a rod-like bolt from a disk-like washer, which can share the same shortest/longest ratio.

3.4Training & Evaluation train_shape_gen.py

  • Same leave-one-node-out sampling pattern as NodeRanker, against the frozen encoder — 60 epochs, continuous-angle rotation + scale/occupancy jitter augmentation.
  • Metrics: voxel IoU (deterministic, full-grid) and a chamfer-distance proxy over occupied-voxel centroid clouds.
  • R36 code landed, retrain pending Chamfer's point-cloud subsampling now uses a fixed-seed generator instead of the global RNG — re-evaluating the same checkpoint on the same voxel grid used to give a different chamfer every call once a shape exceeded 300 occupied voxels (measured ~110% coefficient of variation from sampling noise alone, on top of real model variance). Landed in the R36 commit; Phase 3 hasn't been retrained since, so not yet exercised against real data.
  • R36 code landed, retrain pending Checkpoint selection now uses score = IoU − 2.0×chamfer instead of IoU alone — the old selection was observed passing over a near-IoU-tied epoch with ~20% better chamfer purely because IoU ticked up slightly on a different epoch.

Supporting — AssemblyTemplateDB assembly_templates.py

A frequency prior, independent of the GNN entirely: median component-type counts per category, computed once from the training corpus.

  1. build() groups all processed graphs by category (walking past known container directories in the source path) and computes the median count of each of the 8 types per category.
  2. At inference, match() compares an uploaded assembly's observed type counts against every category template and returns the best fit + a confidence score.
  3. get_missing() then reports expected − observed per type as the text-only "Expected Components Missing" panel — this is what still covers non-fastener types after Phase 3's shape generation was scoped down to fasteners only.

Supporting — Open-Surface & Hole Detection surface_analyzer.py

Finds where on the 3D model a component is likely missing — two independent detection paths that both run on every uploaded assembly.

Whole-face regions (Octree)

Adapts Borah & Borah (2020)'s block-based regional approach: free (unshared) surfaces above an area-ratio threshold are spatially clustered via a lightweight 3D octree, keeping the highest-area-ratio representative per leaf — flags large open regions like an unfilled housing face.

Per-hole fastener candidates

Every free cylindrical face is independently checked as a bolt/screw-hole candidate: diameter (2–50mm) and depth (≥1mm) plausibility, then a same-diameter repetition requirement (≥2 instances on the same body — a real bolt pattern repeats; a one-off tool bore doesn't). Coaxial duplicates (a counterbore + its clearance bore) are merged by bore-axis + position tolerance.

Both paths return centroid, bbox, and normal_hint (surface normal or bore axis) per candidate, tagged is_hole true/false — the Streamlit app's shape-generation step (see below) runs directly off the hole candidates now, no longer capped by AssemblyTemplateDB's approximate per-type missing-count prediction.

Supporting — AIDA skills_agent.py

A Gemini-backed agent that explains predictions in engineering language, persona and domain skills defined declaratively in skills/engineering_3d_assembly.yaml (extend by editing that file, not the agent code).

  • Builds a system prompt from the loaded skills profile, then narrates each inference result section (Assembly Type, Not Assembled, Potentially Missing, Expected Components Missing, Next Component, Open Joints, and Suggested Missing-Part Shapes) as structured, section-headed prose.
  • Degrades gracefully without GEMINI_API_KEY set — every other feature still works, only the natural-language explanation is unavailable.

Serving — Streamlit Frontend front_end/app.py

The Streamlit app does not call the FastAPI backend — it runs its own subprocess importing infer.py directly. The API above exists as a separate, independently-usable interface to the same underlying models.

  1. _run_inference() — the full pipeline per upload: parse STEP → classify components → run the GNN+LinkPredictor for missing-link detection → NodeRanker for next-component → AssemblyTemplateDB for expected-missing counts → surface_analyzer.py for open-joint/hole detection → HybridShapeGenerator for shape-gen ghost meshes on detected fastener holes.
  2. _build_panel_sections() — collapsible results UI: Assembly Type, Not Assembled, Potentially Missing, Expected Components Missing, Next Component, Open Joints, Suggested Shapes.
  3. _run_aida_explain() — sends the structured result to AIDA for natural-language narration.
  4. Dual 3D viewer (Plotly): Original/Result toggle, Highlight on/off, legend grouped by overlay category with per-group select-all, each item independently selectable.
